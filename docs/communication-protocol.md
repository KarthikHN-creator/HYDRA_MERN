# HYDRA Application Communication Protocol (Draft)

**Status:** Draft for review; not implemented or verified with hardware.

This document proposes a shared JSON message format for the React PWA, Node.js service, and ESP32 firmware. It does not define a transport implementation. The first hardware test is planned to use local Wi-Fi directly between the PWA and ESP32; the Node.js relay can be added after that link is stable.

## Design rules

- Use JSON objects with a `type` field to identify each message.
- Every command must include a unique `messageId`, generated by its sender. Reuse of an ID for a different command is invalid. The ID format is not yet fixed.
- Servo numbers are one-based and limited to `1` through `6`. The seventh PCB servo output is unused.
- An angle is a requested target in degrees. Firmware must enforce its mechanically calibrated safe limit for that servo. The safe limits are not yet known; clients must not assume that the full 0 to 180 degree range is safe.
- A software `STOP` command requests that firmware stop or inhibit motion according to finalized firmware behavior. It is not a physical emergency stop.
- Missing or unknown hardware readings must be represented as `null` or an explicit unavailable state, never as a fabricated healthy reading.

## Commands

### Set one servo target

```json
{
  "type": "servo",
  "messageId": "cmd-unique-id",
  "servo": 1,
  "angle": 90
}
```

`messageId` identifies this command and is used to correlate its acknowledgements. `servo` must be an integer from 1 through 6. `angle` must be numeric and finite. Firmware is responsible for rejecting targets outside the calibrated safe range and for applying controlled movement where appropriate. The calibrated limits and whether fractional degrees are supported remain to be decided.

### Request an action

```json
{
  "type": "action",
  "messageId": "cmd-another-unique-id",
  "command": "STOP"
}
```

The initial command identifiers from `specs.md` are `MOVE_LEFT`, `MOVE_RIGHT`, `MOVE_UP`, `MOVE_DOWN`, `START`, `DRINK_WATER`, and `STOP`. Voice phrase mapping stays in the laptop voice component. The exact arm behavior for each action identifier must be defined before it can move hardware. In particular, `STOP` requests that motion stop, but its exact response is not finalized: whether it holds position, disables servo output, or does something else must be decided and tested before any hardware operation. Do not assume that cutting servo power is always the safest response; the arm may fall under gravity. A software `STOP` is not a substitute for the physical emergency-stop method.

## Acknowledgements

The receiver returns an `ack` message using the command's `messageId` so the sender can identify which command the status belongs to.

```json
{
  "type": "ack",
  "messageId": "cmd-unique-id",
  "status": "accepted",
  "error": null
}
```

The `status` must be one of:

- `accepted` - the command passed initial validation and was accepted for processing. This does not mean it has finished or that the requested physical movement occurred.
- `rejected` - the receiver refused the command, for example because it was malformed, unsupported, or outside configured safe limits. This is a terminal status for that command.
- `completed` - processing finished successfully according to the receiver. This alone does not verify physical position unless the hardware provides and validates that feedback.
- `failed` - processing started or was accepted but could not be completed. `error` may contain a concise machine-readable or human-readable reason; its format is to be finalized. For statuses without an error, `error` is `null`.

For a command that proceeds, `accepted` may be followed by a terminal `completed` or `failed` acknowledgement. A command that is `rejected` has no later status. Acknowledgement timing, duplicate handling, and retry behavior still need agreement. Senders must correlate acknowledgements by `messageId` and must not treat `accepted` as completion.

## Telemetry

```json
{
  "type": "telemetry",
  "connected": true,
  "obstacleDetected": null,
  "servoAngles": [90, 90, 90, 90, 90, 90]
}
```

- `connected` indicates that the reporting controller is reachable; it does not certify that the arm is safe to move.
- `obstacleDetected` is `true`, `false`, or `null` when unavailable or not yet validated.
- `servoAngles` contains six entries in servo-number order. An entry may be `null` if the position is unknown. A reported angle is the controller's available position estimate; it is not proof of independent physical position feedback from the servo.

## Validation and errors

Receivers should reject unknown message types, malformed JSON, missing or invalid `messageId` values, invalid servo numbers, non-finite angles, and unsupported command identifiers. A rejected command should receive a `rejected` acknowledgement when a valid `messageId` can be read. The `error` format, acknowledgement timing, duplicate handling, and retry behavior remain to be finalized before integration.

## Connection loss

When communication is lost, the system must stop accepting new movement commands. The physical response of the arm to connection loss must be defined and tested before operating the arm. Movement commands that were sent but not confirmed as completed must never be replayed or executed from a queue after reconnection. On reconnection, the sender and receiver must discard stale queued movement commands and require fresh commands from the user or controlling application. Reconnection does not imply that the arm is in a known or safe state; status must be re-established before movement is enabled. The exact status-recovery handshake remains undecided.

## Decisions needed before hardware integration

- Finalize safe minimum and maximum angle for each servo after mechanical calibration.
- Finalize the `messageId` format, `error` detail, acknowledgement timing, duplicate handling, and retry behavior.
- Define and test the `STOP` behavior before hardware operation, including how the arm is supported if servo output is disabled.
- Define obstacle detection, stop, and recovery behavior.
- Define and test the physical response to connection loss, plus the status-recovery handshake after stale movement commands are discarded.
- Select the transport details for direct local Wi-Fi communication.
- Define the action behavior for each application command identifier.

Until these decisions are reviewed and firmware behavior is tested, treat this as a proposed software contract only. Do not use it as evidence that any hardware behavior is implemented or safe.
